# In the wild — what two real projects do about this, and whether it works

Two projects by the same maintainer meet the curtain from opposite sides. Both
excerpts are cleaned copies of shipping code (September 2026), with a verdict.

| file | project | side of the curtain | verdict (4 Sep 2026) |
|---|---|---|---|
| [`ensure_materialised.py`](ensure_materialised.py) | Bristlenose (a Mac app + Python sidecar that *reads* a user's recordings, which may live in iCloud Drive / OneDrive / Dropbox) | **reader** — needs the bytes, is happy to wait, must not wait forever | **Working.** Detect with `SF_DATALESS`, fault in with a 1-byte read on a bounded thread, name the provider in the log. The `on_wait` hook for a "downloading…" label is wired by none of its five callers yet. |
| [`policy-canary-test.swift`](policy-canary-test.swift) | Bristlenose | reader | **Working, and the important one.** A unit test that asserts the sandboxed app runs with materialisation **ON** (2). Every design conclusion rests on that number, so it is pinned: if a launch path stops inheriting ON, the suite goes red instead of the app silently switching from "hangs" to "EDEADLK". |
| *(not excerpted)* `CopyMachinery.swift` — `FileManager.copyItem` | Bristlenose | reader (copying a recording *out* of iCloud into the project) | **Not working.** Bare `copyItem` on an evicted source blocks with no bound under ON — the June 2026 hang. The fix shape is decided (detect → `startDownloadingUbiquitousItem` → poll with a wall-clock bound → copy, mirroring the Python) and not yet built. `NSFileCoordinator` was ruled out: under ON a coordinated read materialises exactly as an uncoordinated one does. |
| [`write_beside_then_rename.sh`](write_beside_then_rename.sh) | Stickleback (an rsync-shaped backup of `~/Code` *into* iCloud Drive, from a launchd agent) | **writer** — must never read the destination, must never leave the file in neither place | **Working per file.** Temp name beside the destination, then `mv` onto the placeholder. Retired an earlier `rm`-first version that was correct for rsync and wrong for a sync destination. |
| *(not excerpted)* `lib-rsync.sh::run_rsync` — five-pass loop, excluding each blocker between passes | Stickleback | writer | **Not working, by construction.** The bulk pass is openrsync, which mmaps every changed file's stale copy; under launchd (policy OFF) each pass dies at the *next* evicted file, so the loop is delay plus one new blocker per pass, and everything after the fifth blocker is silently left stale. Diagnosed 4 Sep 2026: it "failed to reproduce" for four days because reproduction attempts were run by hand, i.e. under ON. Open decision: `MaterializeDatalessFiles` in the plist (one line; downloads stale bytes it is about to overwrite) vs. an own copier that lists changes with `--dry-run` and applies the per-file shape above. |
| [`icloud-status.swift`](icloud-status.swift) | Stickleback | writer — the *verifier* | **Working, after one expensive lesson.** The only per-file "is it uploaded?" answer with no ubiquity container is `URLResourceValues.ubiquitousItemIsUploaded`. It returns **nil** — not false — for files *inside a package*, because iCloud tracks a bundle as one item; counting nil as pending produced a permanent 122-file false alarm on a fully-uploaded mirror. Ask about the package, never its contents. |
| *(not excerpted)* `verify-backup.sh` — a `--dry-run` of the real copy, source vs. mirror | Stickleback | writer — the *honesty* | **Working, and it is the part that matters.** Every liveness check ("the job ran", "the log says finished", "the snapshot hashes match itself") passed on 105 of 116 runs that were silently partial. Comparing source to copy by metadata is what turned a green tick under a red alarm into a number. |

**The pattern across both:** metadata is always safe (`stat`, `SF_DATALESS`,
`URLResourceValues`); the bytes are where the policy bites; and the tools that work
are the ones that decided *which side of the curtain they are on* and stayed there.
