# Measured 4 Sep 2026 — macOS 26.4.1, Apple silicon, APFS, iCloud Drive with Optimise Mac Storage ON

Verbatim probe output, with home-directory and cloud paths shortened to `~`,
`<icloud>` (`~/Library/Mobile Documents/com~apple~CloudDocs`) and `<dropbox>`
(`~/Library/CloudStorage/Dropbox`). Nothing else edited.

## 1. Which policy does a process inherit?

`policy-probe.swift`, same binary, two launch paths:

```
# from a shell descended from a GUI app (Terminal / Claude.app)
policy process=2 (ON=2 OFF=1) EDEADLK=11

# the same binary via `launchctl submit` (i.e. how a LaunchAgent runs)
policy process=1 (ON=2 OFF=1) EDEADLK=11
```

The sandboxed test host of a Mac app measured **2 (ON)** the same morning
(`getiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_PROCESS)`).

## 2. Which operations touch a placeholder — `ops-probe.c`

Run under launchd (policy OFF), on a 198-byte placeholder:

```
getiopolicy(process)=1 thread=0
  before: st_flags=0x40000060 dataless=1 size=198 blocks=0
  getattrlist: 0 errno=0
  open ok
  after-open: st_flags=0x40000060 dataless=1 size=198 blocks=0
  fcntl F_NOCACHE -> 0
  mmap: mmap FAILED errno=11 Resource deadlock avoided
  after-mmap: st_flags=0x40000060 dataless=1 size=198 blocks=0
```

Same probe from a GUI-descended shell (policy ON): `mmap ok`, and the file's
flags went `0x40000060 → 0x40` with `blocks 0 → 8` **before any page was touched** —
the `mmap()` call itself downloaded it. Under OFF, `pread`, `clonefile` (dataless
source) and `copyfile(COPYFILE_ALL)` all returned `EDEADLK` (errno 11) and left the
file dataless. `lstat`, `getattrlist`, `open(O_RDONLY)` and `fcntl(F_NOCACHE)`
succeeded under both policies without materialising.

## 4. `brctl download` / `brctl evict` — hidden but working

`brctl` with no arguments prints a usage that lists only `diagnose` and `log`.
With a path, on a 608-byte placeholder:

```
before: compressed,dataless size=608
=== brctl download
rc=0
after download (2 s later): compressed,dataless size=608     ← asynchronous
=== brctl evict
evicted content of '<icloud>/Code-backups/vmtools fix'
rc=0
after evict (2 s later): - size=608                           ← the download landed AFTER the evict
settled (10 s later): - size=608
=== brctl evict (again)
evicted content of '<icloud>/Code-backups/vmtools fix'
after 2nd evict: compressed,dataless
```

Two runs the same morning that called `brctl download` and `brctl evict` **without
a path** got the usage text and concluded the subcommands were gone. They are not;
they are undocumented.

## 5. Eviction in the wild

- A 36,201-file iCloud Drive folder had **31,134** placeholders with **189 GiB free**
  on a 926 GiB disk. Eviction is not driven by free space here.
- Re-eviction after materialising: three files went back within **2 minutes** (1 Sep);
  two others were **still local after 4 minutes** (4 Sep). There is no clock to plan
  around.

## 6. openrsync, under launchd

`rsync -aW --delete <local> <icloud>` from a LaunchAgent, five passes, each dying on
a *different* changed file whose placeholder it tried to hash:

```
rsync(86752): error: <repo>/.git/logs/refs/heads/<branch>: mmap: Resource deadlock avoided
rsync(86750): error: unexpected end of file
```

Every file after the aborting one was silently left stale. The same command from a
Terminal window completes, because the Terminal-spawned rsync runs with
materialisation ON and its `mmap` downloads the placeholder instead of failing.
