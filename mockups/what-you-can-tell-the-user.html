What you can tell the user about an evicted file

iCloud Drive lets people stop caring where their data is — local or in the cloud, kept either way, never limited by the device or by free space — while keeping the familiar surface of a disk with files in folders. That is a goal worth applauding, and for almost every app the abstraction is exactly right; this page is not an argument against it. It is for the moment an app has to set an expectation anyway — a wait, a verdict, a promise — and wants to do that with the truth, without misleading anyone and without breaking the mental model the system has built. Here is the inventory. Every row names the API it stands on, or the search that found none. Measured on macOS 26.4.1, 4 September 2026; macOS 27 changes none of it.

POSSIBLE What you can honestly show

Everything here is metadata, or a bound you set yourself.

Waiting for iCloud Drive…interview-07.mp4 · 1.2 GB
MEASURED · SF_DATALESS in st_flags says it is a placeholder, ubiquitousItemIsDownloading (a Bool, iCloud only) says the fetch is in flight, startDownloadingUbiquitousItem asked for it in 1–3 ms.
Downloading from OneDrive…no progress is available from this provider
MEASURED · the flag is provider-agnostic; for Google Drive / OneDrive / Dropbox the label is all you get — say so rather than fake a bar.
Still waiting after 5 minutesiCloud has not delivered interview-07.mp4 yet
MEASURED · a wall-clock bound around the blocking read (policy ON) or a poll after startDownloadingUbiquitousItem. The bound is yours; the OS offers none. "Skip" takes effect at the next file — nothing cancels inside a blocking copy.
All 36,201 files uploaded21 still uploading · checked 40 s ago
MEASURED · per-file URLResourceValues.ubiquitousItemIsUploaded / IsUploading, no ubiquity container needed. Count a package as one item — its contents answer nil, not false.
99% copied, not yet safe522 files missing from the mirror · last complete backup 2 days ago
MEASURED · a dry run of the real copy, source against mirror, by size and mtime — never by reading mirror bytes. This is the only sentence that answers "is my stuff in there?"
Kept locally — 31,134 of 36,201 files are in the cloud onlyreading any of them will download it first
MEASURED · one stat per file, no side effects. You can always count placeholders; you cannot promise what the count will be tomorrow.

NOT POSSIBLE What no public API supports

Two research passes and Apple's own headers: nothing to build these from.

Downloading… 40%Google Drive / OneDrive / Dropbox
NOT FOUND · no per-file percent for third-party File Providers. st_blocks reads 0 until it reads 100% — providers stage the download and swap the file in atomically.
Downloading… 40%iCloud Drive, from a sandboxed app
UNMEASURED · NSMetadataUbiquitousItemPercentDownloadedKey exists on paper; whether a sandboxed third-party app can read it for a file outside its container on a File-Provider-backed iCloud is the one open probe. Until measured, this row lives here.
Cancelmid-file
MEASURED · a blocking read or copyItem parks in the kernel with no timeout; Task.cancel() cannot break it. Only your own bound returns control, at the next file boundary.
About 2 minutes remainingETA
NOT FOUND · no rate, no percent, no queue position. Finder's own pie comes from the provider extension's Progress, which the system consumes and does not republish.
These files will stay downloadeda promise about eviction
MEASURED · re-eviction after materialising took 2 minutes once and more than 4 minutes another time; there is no clock. Finder's Keep Downloaded sets an undocumented xattr with no API and a ten-item limit. You may ask (startDownloadingUbiquitousItem); you may not promise.
You have plenty of free space, so nothing will be evicted
MEASURED · 31,134 of 36,201 files were evicted with 189 GiB free on a 926 GiB disk. Eviction here follows age of access, and Apple publishes no threshold.

MISLEADING Easy to render, reads as reassurance, and is not true

Each of these has shipped somewhere, in good faith. The fix is usually one honest word more, not less UI.

Backed up ✓the job ran and exited
A launchd job that spawned, wrote a log line and exited 0 has proved that a job ran. Under launchd the copier runs with materialisation off; openrsync hit one evicted file, aborted, and left every later file stale — with exit status from the last stage of a pipeline. "Ran" is not "copied"; "copied" is not "uploaded".
Importing…no bound, no provider named
A spinner over a blocking read is the June-2026 hang: under policy ON the syscall waits forever for a provider that may never answer, and the app has told the user nothing it could have told them — which store, that it is a download, and when it will give up.
Downloaded 100%size matches
st_size is the logical size and is correct on a placeholder with zero bytes on disk. Only SF_DATALESS (or totalFileAllocatedSize == 0) tells you the bytes are not here.
All backups healthychecked 4 days ago
A green headline over a stale check. The checker itself had been unable to start for four days; nothing it said was current. A verdict must carry its age, and an old verdict is not a verdict.
Optimise Mac Storage keeps your recent files on this Mac
Apple's wording is "when space is needed" and "recent files"; neither is defined, and the measured behaviour is eviction by age regardless of space. Present it as the system's description of its own behaviour, never as your app's guarantee.
Companion to the ground-truth README. The reader/writer split matters: a reader may wait and should say for whom; a writer must never read the destination and must verify by metadata. What both may always do is count placeholders, name the provider, set a bound, and carry the age of every verdict.
